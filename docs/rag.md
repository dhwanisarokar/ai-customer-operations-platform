# Retrieval-augmented generation (RAG)

```text
customer message
   -> query text (latest customer message, bounded)
   -> embedding (Gemini, purpose = query, 768 dims, L2-normalized)
   -> PostgreSQL + pgvector: cosine similarity over THIS organization's PUBLISHED chunks
   -> top K above the relevance threshold (with document id/title, chunk id/index, similarity)
   -> grounded prompt -> Gemini -> validated reply + the sources it cited
```

Everything runs on PostgreSQL (Supabase) with the `vector` extension. No external vector database.

## Embeddings

| Setting           | Value                                                                                                      |
| ----------------- | ---------------------------------------------------------------------------------------------------------- |
| Model             | `gemini-embedding-2` (override with `GEMINI_EMBEDDING_MODEL`; one definition in `src/server/ai/config.ts`) |
| Stored dimensions | **768** (`vector(768)`), fixed in the schema, see below                                                    |
| Normalization     | Vectors are L2-normalized before storage and querying                                                      |
| Purpose           | Documents and queries are embedded differently (see below)                                                 |

**Why 768.** The Gemini embedding models return 3072 dimensions by default and support truncation
to smaller sizes (768 and 1536 are recommended). 768 stores 4x less data than 3072 (about 3 KB per
chunk instead of 12 KB), scans faster and keeps indexes small, with a small quality loss that is
acceptable for support articles. It is a database fact (the column type), not an environment
setting: changing it needs a migration and re-embedding every chunk. Wrong-sized or non-finite
vectors are rejected in code (`validateEmbedding`) and again by PostgreSQL.

**Document vs query.** Retrieval quality depends on telling the model which side of the pair a text
is. Older embedding models take a `taskType` parameter; `gemini-embedding-2` is steered by a text
prefix instead (`task: search result | query: ...` for queries, `title: ... | text: ...` for
documents). `src/server/ai/gemini/embeddings.ts` picks the right form per model.

**A SDK pitfall we hit and fixed.** `gemini-embedding-2` is multimodal and treats a plain
`string[]` as parts of ONE input, returning a single embedding for the whole batch. The provider now
sends one `Content` object per text, and verifies that N texts yielded N vectors (a test pins this).

## Similarity search

```sql
SELECT c.id, c."documentId", d.title, c."chunkIndex", c.content,
       1 - (c.embedding <=> $query::vector) AS similarity
FROM knowledge_document_chunks c
JOIN knowledge_documents d ON d.id = c."documentId" AND d."organizationId" = c."organizationId"
WHERE c."organizationId" = $org
  AND d."organizationId" = $org
  AND d.status = 'PUBLISHED'
  AND c."contentVersion" = d."contentVersion"
  AND (1 - (c.embedding <=> $query::vector)) >= $threshold
ORDER BY c.embedding <=> $query::vector, c."chunkIndex"
LIMIT $k
```

- **Metric:** cosine similarity (`<=>` is pgvector's cosine _distance_; similarity = 1 - distance).
  Cosine ignores vector length and is the metric these models are trained for.
- **Tenant first:** the organization comes from the verified session; the query filters
  `organizationId` on both tables and joins through the composite key.
- **Published only, current version only:** drafts, archived documents and stale vectors are
  excluded in SQL.
- **All in PostgreSQL:** ranking, threshold and limit are SQL. Nothing is ranked in JavaScript.
- All values are bound parameters; the vector literal is generated by code that only accepts a
  finite 768-number array.
- Embeddings are never selected into results or sent to a client.

### Why no HNSW/IVFFlat index (yet)

Approximate indexes are fast, but with a tenant filter they search first and filter afterwards, so a
small organization in a large table can get fewer results than exist (or none). This is a known
multi-tenant hazard. Today every query is scoped to one organization's chunks (hundreds, not
millions), and an exact scan over that slice using the `(organizationId, documentId)` index is both
correct and fast. Revisit when a single tenant reaches tens of thousands of chunks: options are
pgvector 0.8 iterative scans, partial/partitioned indexes per large tenant, or an index on an
`(organizationId)`-prefixed expression. Use `EXPLAIN ANALYZE` on real data before choosing.

## Relevance threshold

Results below `RAG_MIN_SIMILARITY` (default **0.60**) are dropped, so "nothing relevant" is a real
outcome and the agent says it lacks information instead of stretching weak matches.

How the default was chosen (and what it is not): one measurement against the live API with
`gemini-embedding-2` at 768 dimensions on 6 short support articles and 8 questions (6 on-topic
paraphrases, 2 off-topic). Relevant pairs scored **0.68 to 0.81**; off-topic questions scored at
most **0.55**; on-topic questions against the _wrong_ article scored up to **0.65**. The top-ranked
document was correct in all 6 on-topic cases. 0.60 rejects the off-topic noise while keeping recall
for paraphrases, and the model is a second filter (it must cite what it uses and may decline). It is
a starting point from a small sample, not an optimum: collect real questions with known answers,
plot the score distributions and tune. `npm run ai:smoke` prints scores for a quick re-check, and
the value can be changed without a deploy of code via the environment variable.

## Retrieval service

`searchKnowledge({ organizationId, query, limit, minSimilarity? })` in
`src/server/services/knowledge-retrieval.ts` is an internal service, deliberately not an API route.
It returns `documentId, documentTitle, chunkId, chunkIndex, content, similarity` and logs only
counts and scores (never the query text).

## Failure behaviour

- Query embedding fails or returns an invalid vector: the AI request fails with a safe `502`, and
  nothing is stored.
- No chunk passes the threshold: retrieval returns `[]`; the agent is told "no relevant knowledge"
  and replies with uncertainty (see [ai-agent.md](ai-agent.md)).

## Future work
